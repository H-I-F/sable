# 预发版性能基准报告

**引擎：** sable 0.1.0 · **日期：** 2026-10-30 · **机器：** AMD EPYC 9K65、32 vCPU、
Linux 6.6.117（容器，overlayfs）· **Python：** 3.11.1（CPython，GIL 开启）

*以 `benchmark-2024.md` 发布；下面每个数字都来自 2026-10-30 在上述机器上的预发版运行。*

> 这份报告里的每个数字，都由当天提交在 `benchmarks/` 下的脚本、在这台机器上产出。没有从别的
> 机器搬来的、没有从别的数据集外推的、也没有估算的。某个量在多次运行之间会漂移时，发布的是
> 区间而不是单点，并写明这个区间覆盖了多少次运行。

## 摘要

| 测量项 | 数字 |
| --- | --- |
| 持久顺序写（每次 `put` 都 fsync） | **198–219 records/s**，每次确认写 4.6 ms |
| 分组提交写（每 32 次一次 fsync） | **6,310–6,593 records/s** |
| 非持久写 | **102,398–117,160 records/s** |
| 随机点读，键存在 | **p50 38.7–41.4 µs，p99 77.8–97.8 µs** |
| 随机点读，键不存在 | **p50 8.2–9.0 µs，p99 18.4–21.6 µs** |
| Flush memtable 到 L0（110 B 记录） | **81,312 records/s** |
| 全扫描，5,000 键，单线程 | **96–98 scans/s** |
| 写放大 | **3.54x** |
| 空间放大，单代 | **1.17x** |
| 空间放大，一次未 compaction 的全量覆盖 | **2.35x** |
| 读放大，一个归并后的 run | **1.00 block/read**（42.7x payload） |
| 读放大，六个重叠 L0 文件 | 缺席 **5.99 block/read**，命中 **3.49** |

一句话：这个引擎每个已确认写入都 fsync，所以持久写只有每秒几百条；点读从 page cache 里约
40 µs 出来；三个放大系数都是分层 LSM 树的教科书数值——写 3.5x、常驻 1.17x。最让读者意外的
会是并发那个数：六个线程并行读，聚合吞吐并不比一个线程高，而这赖解释器，不赖引擎。

## 1. 这些数字怎么来的

| 脚本 | 数据集 | 回答什么问题 |
| --- | --- | --- |
| `benchmarks/bench_engine.py` | 5,000 键 × 64 B，4 KiB 块，L0 trigger 4 | 每个原语的成本：put、flush、get、scan、compaction、reopen |
| `benchmarks/bench_wal_throughput.py` | 1,000 记录 × 64 B | 持久性要花多少，批量或去掉它能买回什么 |
| `benchmarks/bench_concurrent.py` | 4,000 键，4 reader + 2 scanner，每阶段 2.0 s | 线程能否扩展，compaction 对延迟做了什么 |
| `benchmarks/bench_read_amplification.py` | 4,000 键 × 96 B，每格 2,000 次探测 | 一次逻辑读要几个数据块，按布局和过滤器分 |

四条规则在四个脚本里都成立，而且每条都会改变答案：

- **单进程，不玩预热。** page cache 就是上一阶段留下的样子；每个脚本的第一阶段是把它填满的写入。
  因此这里的一个数字是*缓存后*的读，也就是真实的读多写少负载所面对的读。
- **探测顺序随机化、种子固定。** 每个脚本里 `RANDOM_SEED = 20261030`，于是两次运行读的是同一个
  序列，只有机器不同。
- **不为摘要数字调参。** 除几何参数（块大小、memtable 预算、L0 trigger）外，`EngineOptions`
  都是库默认值，每个脚本都写明自己覆盖了哪一项、为什么。

## 2. 写路径

### 2.1 持久性就是全部成本

| 模式 | 吞吐 | p50 | p99 | p99.9 |
| --- | --- | --- | --- | --- |
| 持久，每次 `put` fsync | 198–219 rec/s | 4.62 ms | 4.84 ms | 5.09 ms |
| 分组，每 32 次一次 fsync | 6,310–6,593 rec/s | 0.008 ms | 0.042 ms | 4.72 ms |
| 关闭 fsync | 102,398–117,160 rec/s | 0.008 ms | 0.014 ms | 0.024 ms |

区间来自 `bench_wal_throughput` 的三次运行和 `bench_engine` 的两次。表里掉出两个事实：

- **比值是 470–518x。** 关掉 fsync 不是让引擎快 2 倍，是快 500 倍。从调用到 syscall 之间写路径
  做的每一件事——帧上的 CRC32、跳表插入、sequence 分配——放在一次 `fsync` 旁边都是舍入误差。
- **分组模式的尾部和持久模式一样。** 它的 p50 掉了三个数量级，p99.9 却还停在 4.7 ms：那就是
  轮到它付 syscall 的那一批。只报平均延迟会把这件事整个藏起来，所以这里每张表都带分位数。

4.6 ms 是这台机器为一次持久写付的价，不是引擎的。它是共享容器文件系统上的 overlayfs；换成
本地 NVMe，同样的代码路径报出来的会是它的一小部分。把它当成引擎性质来引用是错的，所以这一节
把*比值*作为结论、把绝对值作为机器事实。

### 2.2 这 4.6 ms 买到了什么

每个已确认写入按构造都能活过崩溃：一帧 WAL、覆盖 payload 的 CRC32、调用返回前 `fsync`。
对那份 5,000 键的存储，`reopen + replay` 是 **1,074 openings/s**（每次 open 0.93 ms），因为恢复
就是对一个已经在 page cache 里的文件做带 CRC 校验的顺序重放。恢复便宜，才是 fsync-per-write
即便*跑起来*贵、也仍然*设计得起*的原因。

### 2.3 非持久的上限是解释器

102,398 records/s、每帧 95 字节，是 **9.7 MB/s**，也就是每条记录 9.8 µs 的活。这不是磁盘数字
——慢成这样的磁盘是坏的。这是一个 CPython 线程打一个帧（`<IQBII`）、算 CRC32、插进跳表、
更新计数器所要付的代价。任何打算超过单核约 100k 写/s 的负载，都得批量或者换语言，而这个上限
不在 WAL 层。

## 3. 读路径

### 3.1 点读

两次用的是同一份数据集（50,000 键 × 96 B，排空到一个 L1 run），各 20,000 次探测，逐次计时，
区间跨三次运行：

| 探测 | p50 | p99 | p99.9 |
| --- | --- | --- | --- |
| 键存在 | 38.7–41.4 µs | 77.8–97.8 µs | 97.8–110.4 µs |
| 键不存在 | 8.2–9.0 µs | 18.4–21.6 µs | 62.7–94.6 µs |

`bench_engine` 以吞吐的形式量出同一个差距：**命中 21,222 gets/s，缺席 117,290，比值 5.53x。**
两套独立的测量对 Bloom filter 的价值给出一致结论，正是两个都跑的意义。

### 3.2 为什么命中比缺席贵五倍

一次缺席用三步解决，一步都不碰数据块：memtable 未命中、在内存里对稀疏索引二分、问 Bloom
filter 得到 `False`。一次命中跑完同样三步，然后为第四步付账——读一个 4 KiB 块、算它的 CRC32、
解出最多约 30 条记录、逐条比键直到匹配。39 µs 里有 30 µs 是这第四步。过滤器并没有让读变快，
它让*缺席*的读免费；在一个命中率真实的负载里，两行会混成介于两者之间的一个数。

### 3.3 读放大

来自 `bench_read_amplification`，每格 2,000 次探测，两种布局放的是同一份数据：

| 布局 | 过滤器 | 探测 | 跨度内文件数 | 每次探测的块读 |
| --- | --- | --- | --- | --- |
| 重叠（6 × L0） | 关 | 缺席 | 5.99 | **5.99** |
| 重叠（6 × L0） | 开 | 缺席 | 5.99 | **0.06** |
| 重叠（6 × L0） | 关 | 命中 | 5.99 | **3.49** |
| 重叠（6 × L0） | 开 | 命中 | 5.99 | **1.08** |
| 分层（1 × L1） | 任意 | 命中 | 1.00 | **1.00** |
| 分层（1 × L1） | 开 | 缺席 | 1.00 | **0.01** |

三点读法：

- 没有过滤器，一次缺席探测为每个重叠文件付一次块取——最坏情况恰好等于文件数，没法藏。
- 对*存在*的键，检索从新到旧跑、在装着它的那张表上停下，所以成本就是持有者在那个顺序里的
  位置：平均 6 个文件里的 3.49 个。过滤器把那些更老的文件从账单里拿掉（3.49 → 1.08），
  剩下的 0.08 是过滤器自己在 1% 目标下的误判。
- 归并把跨度从 5.99 个文件压到 1.00，到这一步两类探测都收敛到一次取。这个收敛就是 compaction
  买到的东西，而这份报告里别处都看不见它。

## 4. 三个放大：理论与实测

### 4.1 写放大

50,000 键 ×（14 B key + 96 B value）= 5,500,000 逻辑字节，写一次、flush 一次、归并一次。
物理写出的字节，是每一步之后对文件集做 diff 数出来的：

| 阶段 | 写出的字节 | × 逻辑 |
| --- | --- | --- |
| 每次 `put` 的 WAL 帧（21 B 头 + 110 B 记录） | 6,550,000 | 1.19x |
| Flush memtable → L0 | 6,462,390 | 1.17x |
| 归并 L0 → L1 | 6,461,611 | 1.17x |
| **合计** | **19,474,001** | **3.54x** |

一个键穿过一层的理论地板是 `1 (WAL) + 1 (flush) + 1 (merge) = 3.0`。实测 3.54 正是这个地板
加编码开销，而开销是能对上账的：一帧 WAL 带 21 字节自描述头（131/110 = 1.19x），一条 SSTable
记录带 17 字节头，外加稀疏索引、Bloom filter 和块填充（129.2/110 = 1.17x）。一个键每多穿一层
就再加约 1.17x —— 乘子是按层算的，所以一份跨五层的数据集在稳定前大约写
`1.19 + 6 × 1.17`。

### 4.2 空间放大

| 状态 | 盘上 | × 逻辑 |
| --- | --- | --- |
| 50,000 个新键，5 个 L0 文件 | 6,462,390 | 1.17x |
| 一次全量覆盖之后（10 个 L0 文件） | 12,924,780 | **2.35x** |
| 一次 compaction job 之后 | 6,461,611 | 1.17x |

1.17x 是编码，不是垃圾：每个键只写一次，没有被取代、可回收的东西，差距正是写放大里出现的
那同一份记录头和索引开销。2.35x 是一整代被取代的记录，而且*恰好*是两份拷贝——旧版本和新
版本，没有别的。

这给操作者的是一条规则而不是一个数：**空间放大是每一代未 compaction 的 1.17x。** 本引擎里
compaction 是显式的（ADR-002），所以在有人调 `compact()` 之前，没什么会去回收那 2.35x。一个
每小时覆盖整个键空间、却从不 compact 的 writer，会以每小时 1.17x 的速度把磁盘填满，而再多的
读也不会触发清理。

### 4.3 读放大

地板是块粒度，不是过滤器。一个 96 B 的 value 从 4 KiB 块里端出来，在有任何文件重复之前就已经
是 **42.67x** 放大，而这是实测的最好情况（分层、命中）。未归并、未过滤的命中情形达到
**148.71x** ——同样的粒度惩罚乘以访问过的 3.49 个文件。两个数字来自同一次运行，所以 3.49
不是塞进公式里的估计，是量出来的文件数。

唯一能挪动这个地板的杠杆是块大小，而挪它要在空间和扫描成本上还账。在 96 B 的 value 下，不
存在能让点读变便宜的块大小：该换的是更大的 value 或更宽的读，不是调过滤器。

### 4.4 三者互相抵消

| 机制 | 消掉什么 | 付出什么 |
| --- | --- | --- |
| Bloom filter | 缺席键的读放大（5.99 → 0.06） | 约表大小的 1% |
| Compaction | 读放大（5.99 → 1.00 文件）与空间放大（2.35x → 1.17x） | 写放大：每次归并 +1.17x |
| 更大的块 | 索引大小、块数、seek 次数 | 读放大的地板、扫描解码成本 |

没有任何配置能同时把三者降到最小，而这份报告正是本引擎所做的具体取舍的证据：每次写都 fsync
（接受写成本）、只在被要求时 compact（把空间成本交给操作者）、每张表都留一个 1% 的 Bloom
filter（默认把读成本压到最小）。

## 5. GIL 下的并发

`bench_concurrent` 让 4 个 reader 线程和 2 个 scanner 线程对一个装着 6 个重叠 L0 文件的存储跑
2.0 s，再在 compaction 运行时跑一遍：

| 测量项 | 数字 |
| --- | --- |
| 单线程点读，同一存储 | 20,197–20,435 reads/s |
| 4 reader + 2 scanner，点读 | 20,012–20,434 reads/s 聚合 |
| 单线程 scan（250 键窗口） | 254–280 scans/s |
| 该竞争下的 scan | 2–5 scans/s，p50 121–816 ms |
| compaction 期间的点读 | 无竞争速率的 0.92x |

- **线程不增加读吞吐。** 32 vCPU 机器上六个线程，对同一份存储（6 个 L0 文件、sequence
  23,999、同一份探测列表）只交付单线程的 0.98x：20,012–20,434 reads/s 对 20,197–20,435。
  每次 `get` 一生都耗在字节码里，一点都不等一个其实就是 page cache 的设备，于是 GIL 是唯一
  被争用的资源，多线程只增加了切换。
- **扫描塌掉一到两个数量级。** 一次 scan 每块发一次位置读——这一步确实释放 GIL——然后握着
  GIL 在 Python 里解出约 45 条记录。六个线程竞争时，每个块的解码要排在另外五个线程加上 5 ms
  切换间隔后面，实测 p50 在多次运行之间从 121 ms 到 816 ms。这个方差本身就是结论：这是调度，
  不是一个稳定的成本。
- **compaction 几乎不动点读。** 一次归并重写整棵树时还有 0.92x，因为读拿的是引用计数租约、
  从不在 compactor 上阻塞（ADR-003）。全树重写只掉 8%，是设计在起作用。

给用户的老实结论：这个引擎从线程里用是安全的，不会弄坏任何东西，但不会变快。读并行得靠进程，
脚本里那句清理提示（`--switch-interval 0.0005`）把引擎成本与解释器切换分开，供任何想在自己
硬件上证明这一点的人用。

## 6. 这份报告没测什么

- **冷读。** 这里每次读都命中 page cache。一次设备绑定的读会把存储延迟加到 p50 上，并让过滤器
  的命中/缺席比值更偏向缺席——因为缺席省下的会是一次设备往返，而不是一次内存拷贝。
- **真实硬件。** 共享 vCPU 上的容器 overlayfs。比值是有意义的；绝对微秒数是这台机器的，fsync
  那个数尤其如此。
- **多层树。** 50,000 键会落进一个 L1 文件。读放大随一次读必须考虑的层数增长，而这里只量了
  1 个文件对 6 个，不是 1 层对 4 层。
- **压缩与前缀截断。** 本引擎两者都没有，所以 1.17x 的空间数字是地板，不是起点。
- **来自 `EngineStats` 的写放大。** stats 块报告的是当前 WAL 段的 `wal_bytes_written` 而不是
  累计总量，`sstable_bytes_written` 也没有维护。因此上面每个字节数都是每一步之后 diff 文件集
  得来的——精确、可复现，但也意味着这些数字描述的是*这一串*操作，而不是一生总计。

## 7. 复现

```bash
python -m benchmarks.bench_engine                 # 原语表
python -m benchmarks.bench_wal_throughput         # 持久性模式与分位数
python -m benchmarks.bench_concurrent             # 负载下的 GIL 行为
python -m benchmarks.bench_read_amplification     # 读放大矩阵
```

§3.1 的读延迟分位数和 §4 的放大拆解来自一份没有放进树里的测量脚本，因为它只测一种数据集形状；
它短到可以直接贴，存在的意义是被重跑而不是被引用：

```python
import random, statistics, sys, tempfile, time
from pathlib import Path

sys.path.insert(0, "src")
from sable import Engine, EngineOptions
from sable.types import WriteOptions

KEYS, VB, PROBES = 50_000, 96, 20_000


def pct(values, q):
    return values[min(len(values) - 1, int(q * len(values)))]


opts = EngineOptions(memtable_bytes_threshold=4 << 20, block_size_bytes=4096,
                     level0_file_num_compaction_trigger=4)
engine = Engine.open(Path(tempfile.mkdtemp()) / "db", opts)
keys = [f"user:{i:09d}".encode() for i in range(KEYS)]
value = b"v" * VB

for start in range(0, KEYS, 10_000):                       # 5 次 flush，然后排空
    for key in keys[start:start + 10_000]:
        engine.put(key, value, WriteOptions(sync=False))
    engine.flush()
while engine.compact():
    pass

probes = list(keys)
random.Random(20261030).shuffle(probes)
for kind, batch in (("hit", probes[:PROBES]), ("miss", [k + b"~absent" for k in probes[:PROBES]])):
    samples = []
    for key in batch:
        start = time.perf_counter()
        engine.get(key)
        samples.append((time.perf_counter() - start) * 1e6)
    samples.sort()
    print(f"{kind}: p50 {pct(samples, .50):.1f} p99 {pct(samples, .99):.1f} "
          f"p99.9 {pct(samples, .999):.1f} us  mean {statistics.fmean(samples):.1f}")
```

报告由 `main` 在 5e7043a 生成。在决策文档里引用任何绝对数字之前，请先在别的硬件上重跑。
