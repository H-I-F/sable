# ADR-001：WAL 帧完整性使用 CRC32

**状态：** 已接受 —— PR 02 实现，此后未变。

**日期：** 2026-10-24

**决策人：** 引擎维护者

---

## 背景

每个 WAL 帧都需要完整性校验。扫描器用它回答一个别的办法回答不了的问题：*这一帧完整到达稳定
存储了吗？* —— 再往下，还要用它把「从未承诺过」（torn tail）和「承诺过却丢了」（损坏）分开。
参见 [硬核问答](../faq/deep-dive-qa.zh-CN.md) Q1、Q2。

框住这个选择的约束：

1. **只用标准库。** `sable` 是零运行时依赖的纯 Python 参考实现，需要第三方包的校验算法出局。
2. **每次写入的热路径。** 摘要在每次 `put`/`delete` 上跑一遍，位于一次毫秒级的 `fsync` 之前。
   CPU 不是瓶颈，但一个 Python 层的循环到了规模上会变成瓶颈。
3. **可审计。** 帧布局是逐字节写明的，摘要算法必须是读者靠肉眼就能验的，而不是某种「正确性依赖
   信任某个实现」的构造。
4. **威胁模型是介质错误，不是攻击者。** 引擎要扛住半截写入、坏扇区、以及被截断后又被追加的副本。
   它不声称能检测蓄意篡改；没有密钥的校验和都做不到。

---

## 决策

帧头是 `struct.Struct("<IQBII")` —— `crc32 | sequence | op | klen | vlen`。CRC32 覆盖它*自己之后*
的所有东西：剩余 17 个头字节加上 key 和 value。用 `zlib.crc32` 计算、掩到 32 位、以小端存在
偏移 0 处。

`src/sable/wal.py` 里的 `scan_wal_bytes` 对每帧重算一次，并按结果分支。

---

## 考虑过的备选

### 不加校验和

否决。没有它，torn tail 和损坏帧就是同一件事，恢复分不清「丢掉，这个从未被确认过」和「停下，
数据丢了」。引擎只能给两者挑一种行为，而任何一种都有一半时候是错的。

### CRC64

两条独立的理由否决。标准库里没有 CRC64 —— `zlib` 只有 `crc32` 和 `adler32` —— 于是它得是一个
表驱动的 Python 循环，而对每个 value 字节跑 Python 层循环，会压倒一条实际成本只是一次 `fsync`
的写路径。并且边际上的检测提升（对*随机*多位错误是 2⁻⁶⁴ 对 2⁻³²）并不针对真正会发生的错误
类别，那一类是突发（burst），不是随机。

### SHA-256（`hashlib`）

对这个威胁模型属于规格过高，否决。`hashlib` 是 C 支撑的，够快——每字节大约是 `crc32` 的四倍，
放在一次 `fsync` 旁边仍然很小。但它买来的是抗碰撞性，而抗碰撞性防的是「能挑输入来造出指定摘要」
的攻击者。这里要防的是磁盘返回的字节和写进去的不一样。SHA-256 不是错，是工具不对：更贵、需要
更多代码去验证，还暗示了一条本引擎刻意不声称的安全性质。

### 覆盖若干帧的按块校验和

否决。它把这个布局本来要避开的成帧问题又请了回来：校验单位和帧单位不一致，于是「哪些帧可信」
就得再配一张映射表才答得出来。

---

## 为什么偏偏是 CRC32

CRC32 是能完整覆盖真正要紧的错误类别里最便宜的算法。它能检出：

- 所有 32 位及以内的突发错误——这正是坏扇区、掉了一次 DMA 传输、或只落了一半的页的形状；
- 所有翻转了奇数个比特的错误；
- 任意多位错误中除约 2⁻³² 之外的全部。

2⁻³² 这个残余值得老实说一句。按每秒 10 万帧、随机损坏也按这个速率算，大约十几个小时就会漏掉
一次。但真实的存储故障不是这个速率下的随机单比特翻转，而是突发，而 32 位以内的突发是确定性
被抓住的。这个残余正是适合承担风险的地方，下面的缓解措施也框住了它最多能造成什么。

---

## 后果

**正面**

- 每帧一次 C 调用，没有 Python 层循环，没有依赖。
- 摘要一次前向扫描就算完，能在给 key / value 切片分配内存之前先拒掉这一帧。
- 算法靠肉眼、靠任何第三方工具都能验；审计一个文件不需要信任本实现。
- 放在最前面意味着扫描器不必回退 seek，就能算出下一帧偏移并校验它。

**负面**

- 对对抗性或高度随机的损坏有 2⁻³² 的漏检率。
- 不防篡改。能写这个文件的人就能重算 CRC。
- `crc32` 字段自身翻了一位，和 payload 里翻了一位无法区分——两者都表现为不匹配，这也是末尾帧
  被当作 torn tail 处理、而不是假定有人使坏的原因。

**已有的缓解措施**

- SSTable 数据块和索引各自带 CRC32，文件 footer 还会复核头部——所以穿过 WAL 的损坏在数据发布
  之后还有第二次被抓到的机会。
- 如果一帧之后还有存活帧，恢复会抛 `ChecksumMismatchError`，而不是悄悄丢掉它；数据丢失是被
  报告出来的，不是被吸收掉的。
- `strict_tail_crc=True` 供审计「已知生产者只发布完整帧」的文件。

**明确不在范围内**

带认证或带密钥的校验和（HMAC）。防住一个对数据目录有写权限的攻击者是另一个问题；假装一个无密钥
的 CRC 能解决它，才是更糟的错误。
