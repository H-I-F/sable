# ADR-002：Compaction 显式触发，而非后台调度

**状态：** 已接受 —— PR 10 实现，PR 11 细化。

**日期：** 2026-10-25

**决策人：** 引擎维护者

---

## 背景

LSM 树需要 compaction 来给两样东西设上界：一次读必须查的重叠 L0 文件数（读放大），以及再也没人
能读到的版本占着的空间（空间放大）。没有它两者都会无限涨。

通常的答案是后台 compactor 线程。这个项目考虑过，否决了。

本项目特有的约束：

1. **引擎的承诺是可验证的正确性，不是吞吐。** 每个机制存在，都是为了让测试能对下绝对断言。
2. **CPython。** 一个 compactor 线程和它「并行跑着」的 writer 共享 GIL。
3. **测试套件会注入 `SIGKILL`、驱动用 barrier 同步的竞态。** 两者都需要知道维护到底什么时候
   发生过。

---

## 决策

`Engine.compact()` 是一次显式的同步调用：规划、归并、安装恰好一个 job，然后返回它是否做了事。
想要一棵平衡树的调用方自己写循环：

```python
while engine.compact():
    pass
```

有两条路径会隐式调它，都在调用线程内：

- `_maybe_compact()` 在一次由预算触发的 flush 之后运行，用 `acquire(blocking=False)` —— 抢不到
  的 writer 直接返回，不排队。
- `flush()` **不**做 compaction。显式 flush 是一次操作符动作，有可观察的结果；把归并折进去，
  会让层级状态取决于时机，而不是取决于被要求做了什么。

没有 compactor 线程、没有工作队列、没有定时器。

---

## 考虑过的备选

### 后台 compactor 线程

否决。三条理由，按权重排序：

- **失效方式不再可观察。** 一个抛异常的线程没地方报告。它要么静默死掉——树悄悄退化、毫无信号
  ——要么对着一个永远解析不了的输入无限重试。内联调用时，compaction 失败会在造成它的那个线程、
  在造成它的那个点抛出来。对一个全部承诺就是「可验证正确性」的引擎来说，「错误发生在线程外、
  树还在继续跑」不能接受。
- **测试不再确定。** 崩溃矩阵需要知道 kill 之前 compaction 到底完成没有；竞态套件需要 compaction
  和一次 scan 真正重叠。有个不透明的调度器，这类测试每个都得加 sleep 或 hook。有个显式调用，
  `compact()` 返回就是同步点。
- **GIL 把收益封了顶。** 归并是 `heapq.merge` 之上 CPU 密集的 Python。后台线程在 I/O 上买到重叠，
  在其余部分抢 GIL，抢的时刻还不可预测，外加一个线程必须被启动、排空、停下的全部生命周期复杂度。

### 每次写入都内联 compaction

否决。那会让写延迟变成树形状的函数且没有上界。当前设计是在*越过阈值*时 compact，不是每次写，
这样把摊还成本框住了，又没把它藏起来。

### 完全不 compaction

否决。读放大会无限涨，墓碑永远不被物理回收，一个删掉的键会一直占空间。这和「有界、可观察的行为」
这个设计目标直接冲突。

---

## 理由

背压用阈值表达比用调度器表达更好。`EngineOptions` 带着
`level0_file_num_compaction_trigger`、`level0_slowdown_trigger`、`l1_bytes_trigger`、`max_levels`
和 `level_size_multiplier`。策略是数据，而*执行*是一次由操作符掌握的调用。想要自动化的调用方写
那个三行循环，想要确定性的调用方调一次；两边都不必跟对方较劲。

抢不到锁没有代价，所以竞争写成 `acquire(blocking=False)` 而不是阻塞获取。已经握着 compactor
槽位的那一方，正在重写的恰好就是这个调用方本来也会选的文件，阻塞什么也买不到，反而会把一次
吞吐尖峰变成一队 writer 等着别人已经在做的工作。

---

## 后果

**正面**

- Compaction 失败在调用点、在调用线程里浮出来。
- 每个维护步骤都是测试的同步点；竞态套件用 `threading.Barrier` 驱动 compaction 与 scan 对撞，
  断言的是结果，不是时序。
- 没有线程生命周期：没有 start / drain / stop / 关停时 join，也不可能出现 `close()` 之后维护
  还在跑。
- 一串确定调用之后的层级状态是确定的，这才让 compaction 测试能断言精确的文件数。

**负面**

- 一个写很重、却从不调 `compact()` 的负载会攒下重叠的 L0 文件，读放大随之上涨。缓解是机会性的
  （预算触发的 flush 之后跑 `_maybe_compact`），不是保证。
- Compaction 延迟落在越过阈值的那个线程上。那个线程未必是造成压力的线程，所以尾延迟不如有
  专属后台线程时平滑。
- 进程空闲时不会 compaction，因为没有东西触发它。可回收版本占的空间在下一次写入时才收回，
  不是靠定时器。

**接受的取舍**

引擎拿平滑的尾延迟换了可观察的失败和可测试的行为。对一个交付物是「可证明的正确性」的参考实现，
往这个方向偏是对的。生产环境里的嵌入方会自己写那个三行循环放进维护线程，并自行决定怎么报告
一个它已经无法抛出的失败。
