# ADR-004：默认同步刷写 WAL（先写日志后应用）

**状态：** 已接受 —— PR 06 实现，此后未变。

**日期：** 2026-10-24

**决策人：** 引擎维护者

---

## 背景

`put()` 返回必须意味着一件精确的事。可选答案是个光谱：

- 值在 Python buffer 里，
- 值在内核 page cache 里，
- 值在稳定存储上。

只有第三种能同时扛住 `SIGKILL` *和*掉电。引擎的核心承诺——「成功返回的写入在进程死后必须
可读」——需要它，而 `tests/test_crash.py` 的崩溃恢复矩阵正是拿十个不同的 kill 点断言这一点。

这台机器上 `fsync` 大约 4.5 ms。每次写都付这个钱是引擎最大的一笔成本：持久化 223 ops/sec 对
关掉 sync 的 108,687 ops/sec，差 487 倍（记在 README 的基准表里）。

---

## 决策

写路径是**先写日志后应用**，默认同步：

1. 分配一个单调的 sequence，
2. 序列化帧，
3. 对 WAL `write` + `flush` + `fsync`，
4. *之后*才插入 memtable 并返回。

`EngineOptions.default_write_sync` 是 `True`。`WriteOptions(sync=False)` 是逐次调用的覆盖选项，
给那些明知并接受较弱保证的调用方——批量导入、基准、以及 compaction 路径（那里被写的数据在输入
里已经持久了）。

第 3、4 步绝不重排，`Engine._stage_mutation` 跨这两步握着 `_lock`，正是为了让任何观察者都看不到
相反的顺序。

---

## 考虑过的备选

### 异步 fsync、按定时器 fsync

否决。它把一次成功 `put()` 的含义从「持久」改成「N 毫秒内持久」，而不存在一个 N，既小到能保住
崩溃测试、又大到值得这份复杂度。它还引入了一个大小取决于墙钟调度的窗口，而这正是测试套件存在
就是要消灭的那类时序相关行为。

### 组提交（跨并发 writer 批量 fsync）

未采用。它是生产环境的标准答案，也能找回大部分吞吐：一次 `fsync` 覆盖好几个 writer 的帧。代价
是一个队列、一个 batcher 线程或租约，以及——在这里是决定性的——确认不再是调用线程自己的性质。
组提交里的 writer 要等整组 flush 才知道自己的帧持久了；如果组长挂了，调用方不去问就分不清
「已提交」和「丢了」。这是本引擎拒绝让它变得不可观察的一种失效方式。

`WriteOptions(sync=False)` 是写明在文档里的逃生口：它是显式的、逐次调用的，决定由调用方做。

### 写进 WAL 但跳过 fsync，靠 memtable

否决。`SIGKILL` 不会刷 page cache，所以上一次刷盘以来所有已确认的写入都会消失。这正是引擎存在
就是要防住的数据丢失。

### 内存映射的 WAL

否决。`mmap` 让刷盘边界变得隐含：要让写入持久得调 `msync`，而映射把字节到底何时离开进程藏了
起来。一个依赖 `msync` 时机的持久性保证，比显式的 `write` + `fsync` 更难推理，在这些延迟下
也换不来什么。

---

## 理由

持久写入的成本就是稳定存储的成本，引擎不该假装不是。每次 `fsync` 4.5 ms 是磁盘的性质，不是
代码的性质。正确的反应是把这个成本摆出来、并允许退出，而不是把它吸收进一个更弱的默认值。

这个不对称正是设计点：**同步是默认值，因为安全的设置应该是你不问就得到的那个。** 想要吞吐的
调用方传 `sync=False`，他已经做了决定；没想过这件事的调用方，拿到的是持久性。

两份 README 的基准表把两个数字并排列出来，并把那个比值叫作「活过一次崩溃的代价」——成本是
写明而不是藏起来的。

---

## 后果

**正面**

- `put()` 返回只有一个含义，而且是强的那个。
- 崩溃矩阵能断言精确相等——子进程确认过的每个 id 在重开后都可读——而不是一个概率界。
- sequence 分配、WAL 内容、memtable 内容在持久方向上绝不可能不一致：memtable 里的东西都在日志里。
- 保证是逐次调用、本地可验的；没有后台状态。

**负面**

- 吞吐被 `fsync` 延迟框住：参考机器上约 223 ops/sec，而每次操作实际干的活差了五个数量级。
  这是引擎的主要成本，在每个写密集的基准里都看得见。
- `put()` 延迟在竞争下是双峰的，因为一次越过预算的写还得额外付一次 flush。
- 逐次调用的 `sync=False` 可能被误用。README 的持久性章节写明了它会改变「确认」的含义。

**与其他决策的相互作用**

- ADR-001：帧带 CRC32，正因为同步 `fsync` 就是扫描器需要据此推理的持久性边界。
- ADR-002：因为 compaction 是显式的，在输入已经持久时它的输出写用 `sync=False` —— 这个覆盖
  选项正是为它准备的。
- [原子落盘指南](../skills/atomic-flush.md)：同一套 `temp → fsync → replace → fsync(parent)` 纪律
  也用在 SSTable 和 manifest 上，于是持久性故事只有一个版本。
