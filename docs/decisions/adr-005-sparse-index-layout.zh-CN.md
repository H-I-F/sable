# ADR-005：每个 SSTable 尾部的稀疏块级索引

**状态：** 已接受 —— PR 04 实现，PR 08 与 PR 09 细化。

**日期：** 2026-10-24

**决策人：** 引擎维护者

---

## 背景

SSTable 上的点查必须在 `num_entries` 条记录里找到一条，又不能把整个文件读一遍。三样东西要平衡：

- **内存。** 索引在文件打开的整个期间常驻。一个同时开着几千张表的引擎，不可能每条记录留一行
  索引。
- **I/O。** 点查上每多读一个块就是读放大，而这是真正会体现在基准数字里的成本。
- **简单。** 这是一个参考实现，它的布局是要被读的，不只是被用的。

默认块大小 4096 字节（`EngineOptions.block_size_bytes`），所以一张 100 MB 的表大约有 25,000 个块、
可能几百万条记录。

---

## 决策

**每个数据块一行索引**，序列化在数据区之后：

```
block_offset | block_size | first_key_len | block_crc32 | first_key bytes
   uint64        uint32        uint32          uint32
```

`_INDEX_ROW_HEADER = struct.Struct("<QIII")`，定义在 `src/sable/sstable.py`。

查找分两步：

1. **对索引按 `first_key` 二分** —— 纯内存、零 I/O —— 找出唯一可能装着这个键的块。
2. **只读那一个块**，在块内线性扫记录。

索引是懒加载的（第一次有读需要它时才 `_ensure_index`），所以打开一张表不会去解析一个可能永远
不会被查询的文件。

每行都带着该块的 CRC32，于是校验是针对「实际被读的那个块」做的，而不是打开时对整个文件算一次。
Footer 会复核头部 CRC，这才让「一个文件要么完整要么不存在」成为事实而不是愿望。

---

## 考虑过的备选

### 全量索引 —— 每条记录一行

内存上否决。它给出 O(1) 定位、块内零扫描，代价是索引随记录数而不是随文件大小增长。对一个装
几十条记录的 4 KiB 块，那是每张打开的表多出一到两个数量级的常驻内存——而分层树的全部意义就是
很多表同时开着。

I/O 上的差别也比看上去小：全量索引把第 2 步的线性扫描变成一次直接 seek，但第 2 步反正都要读
一个 4 KiB 块。省下的是 CPU，不是 I/O，而在这些延迟下 CPU 不是瓶颈。

### 不建索引 —— 扫整个文件

否决。点查会变成 O(file size)，让读放大正比于表大小。这正是分层设计存在就是要框住的失效方式。

### 在数据区上套 B-tree

对一个不可变文件属于杀鸡用牛刀，否决。B-tree 的复杂度要在结构必须支持增量更新时才值回票价；
一张 SSTable 写一次、永不修改。一个按块 first-key 排好序的数组，给出同样的 `O(log blocks)`
查找，没有指针跳转、没有节点分裂，布局还是读者从头到尾读一遍就能验的。

### 索引放文件头部

否决。数据区写完之前不知道索引多大，所以放头部要么两遍写，要么预留一块可能溢出的固定空间。
放在数据区之后，writer 可以一路流式写下去：造块、记行、序列化索引、再写过滤器块、最后写带上
所有偏移的 footer。

---

## 理由

稀疏索引让索引单位对齐到 I/O 单位。块是文件系统交回来的东西，所以每块一行意味着索引永远不会
指向一个 reader 手上还没有的单位内部。比它更细的都是 CPU 优化，比它更粗的都要多付整次读。

按行带 CRC 是值得单独拎出来讲的一点。打开时校验整个文件，意味着每次 `Engine.open` 都要把每张
表完整读一遍——而 `open` 在恢复路径上，那里延迟最要紧。按块 CRC32 让损坏在遇到它的时候、在
那个地方被检出，对着正要交给调用方的那几个字节验。

---

## 后果

**正面**

- 索引内存是每 4 KiB 一行，与记录数无关。一万张打开的表是几十 MB，不是几 GB。
- 点查在纯内存二分之后，恰好只读一个数据块。
- 范围扫描受益比点查更大：块按 first key 有序，一旦某个块起过了窗口，后面所有块也都过了，
  没有理由再 I/O（`iter_slice` 在第一个不可能装着该范围的块上就返回）。
- 损坏按块检出，坏块会抛异常而不是被悄悄跳过。
- 布局顺序读一遍就能验——没有指进结构中间的指针。

**负面**

- 块内查找是对块内记录的线性扫描。最坏情况是每次点查多做一个块的比较工作，这是 CPU、因此
  便宜，但不是 O(1)。
- 索引的准确度只依赖 `first_key`。一个键只可能在块 *i* 里，当且仅当
  `first_key[i] <= key < first_key[i+1]`，这是精确的——但某个块的 first key 大于目标，并不能
  证明该键在*文件*里不存在；这个情形由 Bloom filter 块（`src/sable/bloom.py`）零 I/O 地回答。
- 每条记录里键是原样存的。没做带重启点的前缀压缩：`EngineOptions.block_restart_interval`
  留在选项面上，但当前没有 writer 路径消费它，所以长公共前缀会多占一些本可以被重启点方案
  收回的字节。
- 改 `block_size_bytes` 会改索引密度，所以用一种块大小写的表用另一种仍可读——索引是自描述的
  ——但性能特征不一样。

**与其他决策的相互作用**

- ADR-001：同一个 CRC32 选择，只是按块而不是按帧用。
- [原子落盘指南](../skills/atomic-flush.md)：索引是那张被原子发布的单一镜像的一部分，这正是
  reader 永远看不到与其数据区不一致的索引的原因。
- Bloom filter 块紧接在索引之后，并且*先于*索引被查询：过滤器给出否定答案就跳过二分和块读，
  这正是实测 5.74 倍「缺席 vs 命中」差距的来源。
